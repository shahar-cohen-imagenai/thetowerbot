## Outcome

Read owned UWs, offered unlock choices, raw levels/values/costs, labs, toggles, cooldowns/durations, plus-system state and account prerequisites.

## Acceptance gate

All nine base UW identities and current observed ownership are represented; lab/subeffect-adjusted values never masquerade as raw stone upgrades.

## Current repository state

- [ ] No graph-level implementation has been certified complete.
- [x] `ultimate_weapons.py` models the UW system and is bound to the one
  recorded capture. `base_identities()` derives the **nine** base weapons from
  the catalog (`domain == "ultimate-weapons"`, `kind == "ultimate-weapon"`);
  the domain's other eight entries are references and strategies and are never
  counted as weapons. Every record represents all nine, in id order.
- [x] `read_page()` reads `tests/fixtures/menu_workshop_ultimate.png`: the
  ULTIMATE UPGRADES heading, the single "New Ultimate Weapon" offer at a cost
  of 5, and the prerequisite "Unlock tournaments by reaching wave 60". That
  capture is an account whose UW system is **locked**, so ownership reads
  `locked` for all nine - distinct from `unknown`, and never `0`. Whether the
  prerequisite is met is `None`: this reader sees the sentence, not the wave
  record. The price's currency stays `None`, because the glyph beside it is an
  icon and the "power stones" sentence lower down is prose, not that price's
  label.
- [x] Raw and adjusted quantities are separately typed and separately
  addressed. `StoneUpgrade` and `AdjustedValue` cannot be placed in each
  other's collection (`TypeError`), a lab identity cannot be a stone upgrade's
  identity (`ValueError`), an `AdjustedValue` must name the lab/substat
  identities behind it, and `raw_stone_upgrade()` is blind to the adjusted
  collection. `decode()` revalidates, so a row edited in the database to move
  an adjusted number into a raw collection is refused on the way out too.
- [x] `account_state.AccountRevision` gained one field, `ultimate_weapons`,
  persisted and restored through `AccountRepository`; a fresh repository and
  `AccountState` over the same sqlite path return the record with the two
  collections still apart. A revision with no UW reading keeps the field
  `None` rather than an empty reading.
- [ ] **Not proven, for want of evidence:** no capture exists of an account
  that owns an Ultimate Weapon. So the owned-page layout, stone upgrade
  levels/values/costs, toggles, cooldowns/durations and the UW+ system are
  read by nothing; they are `unknown` in the model and declared in
  `screen_discovery.capabilities()['unsupported']` as
  `ultimate_weapon_owned_page_layout` (B08),
  `ultimate_weapon_stone_upgrade_rows` (U02),
  `ultimate_weapon_toggles_and_cooldowns` (U03) and `uw_plus_system_state`
  (U04). The `owned` and `not_owned` ownership states exist in the vocabulary
  and no reader produces them yet.
- [x] `screen_discovery.discover()` is unchanged and still refuses this page,
  so B04's guarantee that it can never be parsed as a purchase screen holds.
