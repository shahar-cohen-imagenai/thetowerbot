# B05 — Journal and verify every transaction

**Status:** [ ] Partial — resume
**Domain:** `foundation`
**Dependencies:** [B03](./B03.md), [B04](./B04.md)
**Dependency gate now:** [ ] Blocked until every dependency above is complete

## Outcome

Introduce durable intent, preconditions, one device action, confirmation and reconciliation. Correlate wallet, level/inventory and UI acknowledgement; separate free upgrades and passive income from purchased effects.

## Acceptance gate

A crash after a successful tap does not buy twice; a free upgrade does not falsely confirm a cash purchase; card opening is not logged as bought without evidence.

## Current repository state

- [x] The existing ledger and shopping loop record bounded purchase-related events.
- [x] Landed slice: `transactions.py` holds the durable half of every spend.
  A row in the new `transactions` table is written BEFORE the device action
  and resolved after it, so the window between a tap and its confirmation -
  previously recorded nowhere on disk - now outlives the process. `Stage`
  keeps `INTENDED` (nothing was spent) apart from `ACTED` (one action went
  out, outcome unknown). The journal owns a path and opens a short
  connection per operation, the way `AccountRepository` does, so a session
  built on one thread is usable from the scan loop's.
- [x] Landed slice: one transaction owns exactly one device action
  (`ActionAlreadyTaken`), and no attempt may be opened while an earlier one
  is unanswered (`TransactionInFlight`).
- [x] Landed slice: `transactions.judge` is the whole confirmation rule,
  pure and database-free. `BOUGHT` requires the wallet to have fallen;
  `FREE` is a changed item that cost nothing; `REFUTED` needs both an
  unchanged item and an unmoved wallet; everything else is `UNPROVEN`.
  `spent` stays three-valued - a proven amount, 0 for provably nothing,
  `None` for moved-by-an-unknown-amount - so income landing mid-purchase
  leaves the amount unknown rather than being asserted as the read price.
- [x] Landed slice: both buy paths in `shopping.py` are journalled. A
  workshop row and a card batch each write an intent before tapping, mark
  the action, and resolve against the evidence that follows. A row left
  open by a dead process makes the next visit publish `PurchaseSkipped`
  with reason `unreconciled` and tap nothing; an orderly `reset()` or
  `_end_visit()` resolves what it opened, so one visit is spent
  reconciling and normal operation resumes. `begin()` deliberately does
  NOT resolve - a row open at the start of a visit belongs to a process
  that died, and clearing it there would discard the only record stopping
  a double spend.
- [x] Landed slice: card opening now requires evidence. `PendingCard` holds
  the tap until the gem balance falls by exactly the price; `Purchased`
  with category `CARDS` is no longer published on the same frame as the
  tap. An inconclusive card acknowledgement aborts the visit, as an
  inconclusive workshop one already did.
- [ ] Still required: the ledger does not yet consult the journal's
  verdict. `_record_purchase` publishes `Purchased` carrying the price that
  was READ, so a misread price still reaches `ledger.classify` as a debit
  even when the journal resolved that same attempt `UNPROVEN`. Wiring the
  verdict through to the ledger line - and to `_spent`/`_coin_spent` and
  the visit budget that share it - is the remaining slice.
- [ ] Still required: reconciliation on restart is refusal only. An open
  `ACTED` row is resolved `UNPROVEN` when the visit ends; nothing yet reads
  the wallet to work out what that dead tap actually cost.
